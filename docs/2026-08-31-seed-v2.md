## 1. Why this project exists

Two gaps in the current portfolio, both exposed by the same class of job description — Distributed Systems / Infrastructure Engineer roles at firms building financial platforms, where the recurring asks are event-driven pipelines, large data volumes, systems that are both fast and provably correct, and domain experience in trading, portfolio management, or accounting systems:

**Domain gap.** "Trading systems, portfolio management or accounting systems" recurs as a differentiator across this role class, and nothing in the portfolio is claimable there. Treasury payments is adjacent — money moves, at-most-once holds — but a reviewer from a quant background will not read a payment gate as portfolio accounting. The concepts that *make* portfolio accounting hard (positions as a fold over fills, corporate actions rewriting history, reconciliation against an external statement of truth) are absent as demonstrated artifacts.

**Tooling gap.** Against the recurring "even better" lists in this role class: Go ✅, event-driven ✅, PostgreSQL ✅ — but gRPC ❌, ClickHouse ❌, Kafka ⚠️ Familiar-tier, serverless functions ❌. Familiar-tier tools cannot lead a claim; a scoped, twin-proven lane is what moves one out.

**The thesis fit is the real reason.** These postings ask for systems that are simultaneously fast and irrefutable. Fast is an adjective on the banned-vocabulary list. Irrefutable is a *property* — and it is exactly the property the existing work already demonstrates elsewhere: byte-identical replay, decisions that recompute from a durable feed, gates proven able to fail. A portfolio ledger is the artifact where that property meets this domain. The pitch is never "I built a fast system"; it is "here is a position snapshot, here is the feed it folds from, recompute it yourself — the bytes match."

**Why it's cheap relative to its payoff.** Almost every hard part already exists as a proven pattern in another repo. This is a composition project, not an invention project:

| Needed here | Already proven in | What transplants |
|---|---|---|
| Append-only durable feed, logical clock, no wallclock | intent-plane | Feed semantics, fsync discipline, deterministic replay |
| At-most-once consumption, idempotency by construction | intent-plane + COMPASS PR #7 | Derived idempotency keys; duplicate = refused collision, not caught downstream |
| History that rewrites without lookahead | VANTAGE | Corporate action ≡ restatement; as-of read at viewpoint D returns only what was known by D |
| Independent consumer re-verification | PARALLAX | Reader protocol (never a path or connection string), twin rule, bounded claims via STATUS.md |
| Fail-closed on unevaluable | everywhere | Missing reference data is a refusal, never a silent zero |

The one genuinely new intellectual move: **a corporate action is a restatement of the position history, and the PIT discipline from SEC fundamentals applies unchanged.** A 2:1 split with effective date E, announced date A, processed date P must not alter what an as-of read at any viewpoint before P returns. That sentence is the bridge between BASELINE and this project, and it is the sentence a reviewer who has lived with these systems will recognize as the actual hard problem.

## 2. Thesis candidates (one becomes load-bearing)

1. "A position is not a number in a table. It is a fold over an append-only feed — and anyone holding the feed can recompute it to the byte."
2. "A duplicate fill isn't caught by reconciliation — it's impossible at ingestion."  *(deliberate rhyme with the /intent signature claim)*
3. "Corporate actions rewrite history. The ledger records that history was rewritten — and what every viewpoint saw before it was."

## 3. Target properties — each requires a known-bad twin before it is claimable

Per the standing rule: a gate that has never run red proves nothing. Five properties, five twins, mirroring the rigor-deployment seed structure.

**P1 — At-most-once fill ingestion.**
Idempotency key derived from fill identity (not supplied by the producer); same key + different payload hash = refused collision, durably recorded.
*Twin:* replay the feed with one planted duplicate fill and one planted collision. Duplicate is absorbed with zero position effect; collision lands as exactly one refusal record. Green run shows both; twin count exact, not approximate.

**P2 — Deterministic replay to a byte-identical snapshot.**
Same feed prefix ⇒ identical position snapshot, hash-verifiable. Logical clock only; wallclock never enters the fold.
*Twin:* mutate one event in a copied feed → snapshot hash diverges; reorder two commutative-looking events → either the hash is stable *by proven design* (ordering rule stated and tested) or the divergence is caught. No hand-waving about "order doesn't matter."

**P3 — Corporate actions as PIT-correct restatements.**
Split/dividend applied at effective date but *knowable* only from processed date; as-of read at viewpoint V returns positions as V would have seen them.
*Twin:* plant a split whose effect leaks into a viewpoint before its processed date — the no-lookahead check turns red on exactly the affected rows. This is the VANTAGE exact-planted-count discipline, ported.

**P4 — Fail-closed on unevaluable.**
Valuation with missing reference data (price, FX, action terms) refuses the affected scope — a durable `unevaluable` record, never a silent zero or a stale carry-forward.
*Twin:* withhold one reference row; exactly the dependent positions refuse, everything else stays green.

**P5 — Reconciliation gate proven able to fail.**
Ledger positions reconciled against an independently constructed statement (a second, naive implementation or a fixture "custodian file"); drift is a red gate, not a report.
*Twin:* plant one basis-point of drift in the fixture statement; the gate names the instrument and the amount.

A sixth candidate — **portfolio math correctness** (average cost vs. FIFO lots, realized/unrealized P&L) — is deliberately *not* in v1's property list. It's where scope creep lives. Cost-basis methodology becomes claimable only if v1's five properties are green first. Open question 4.

## 4. Lanes (the BASELINE pattern — empty cells are empty on purpose)

- **Lane 1 — local, Go core.** Feed on disk, fold in Go, snapshots as content-addressed artifacts. All five properties earn both cells here first. This is the only lane v1 promises.
- **Lane 2 — ClickHouse read surface.** Snapshots and as-of position queries served from ClickHouse *behind the existing Reader protocol* — gate checks written against the protocol, never a connection string. Converts a ❌ into a scoped claim ("as-of reads served from ClickHouse, consumer gate green, twin red") without claiming ClickHouse operations expertise.
- **Lane 3 — Kafka transport.** The feed carried over Kafka with the same replay and at-most-once guarantees re-proven across the transport. Moves Kafka out of Familiar, scoped precisely ("feed transported over Kafka; replay and idempotency re-verified end-to-end") — never "production Kafka experience."
- **Explicitly out of every lane:** market connectivity, live data vendors, order management, execution, performance claims of any kind. No production claim, stated on-page, same as /intent.

gRPC note: a gRPC read API over lane 1 is a plausible small addition (Go-native, contract-first, pairs with the OpenAPI discipline elsewhere) — but it is an accessory, not a property. Open question 5.

## 5. Scope walls (write these into the README before writing code)

- **Synthetic fixtures only.** Fills, actions, and custodian statements are checked-in, versioned fixtures — the CLDD "planted ground truth" move. The generator plants the truth; the ledger must recover it.
- **No performance vocabulary.** Banned list applies in full: no "at scale," "high-throughput," "real-time," no latency numbers without a committed benchmark artifact — and no benchmark artifact in v1 at all. The system's speed claim is: replayable and byte-identical. Full stop.
- **STATUS.md is the state of record from the first commit.** Counts, lane status, and claimability live there; README defers to it. (Standing lesson: every repo's README has drifted; STATUS.md hasn't.)
- **CV/site silence until green+red.** Same rule just enforced against intent-workbench. The project earns a /ledger page and a CV line only when the five properties each hold both cells.

## 6. Where it lands when it's real

- Portfolio site: **replaces BASELINE as the site's third system** — "three systems, one discipline" keeps its title and its count. /ledger takes the slot, built on the /baseline page template: thesis line, struts, failure taxonomy, claimability table. Rationale: the ledger *absorbs* BASELINE's core idea (PIT discipline, restatement, the twin rule) and re-lands it in the target domain — showing both would say the same thing twice. The resulting trio: policy (/intent), practice (/rigor), proof-in-domain (/ledger).
- **/baseline stays live, demoted not deleted.** It is a cited surface on shipped CVs (the BASELINE header on multiple live variants links to hossainpazooki.github.io/baseline) and PARALLAX Study 001 leads active application materials — breaking that URL breaks live applications. The ledger page links back to it as lineage: "the PIT discipline this ledger transplants was first proven on SEC fundamentals."
- CV: enters the Distributed Systems / Platform variants as the domain anchor; pairs with intent-plane ("the gate authorizes the irreversible action; the ledger proves what it did to positions"). Displaces CLDD or rigor on space-constrained variants — decide per-variant, not globally.
- Interview surface: the strongest artifact is a recorded terminal session — clone, replay, hash-compare, run the twin, watch it go red. Two minutes, no narration needed.

## 7. Open questions for the brainstorming session

1. **Name.** The family is optics/astronomy (VANTAGE, PARALLAX, BASELINE) or instruments (COMPASS, ATLAS). Candidates: KEEL (what holds the vessel steady), MERIDIAN (the reference line positions are read against), TARE (the zeroing of a scale before measurement), PLUMB (vertical truth). No decision needed to start building.
2. **Corporate-action set for v1.** Proposal: whole-share splits and cash dividends only. Symbol changes, spin-offs, mergers, fractional handling — v2 at the earliest. Is that too thin to be credible, or exactly thin enough to be finishable?
3. **Multi-currency.** FX introduces a second reference-data dependency and doubles P4's surface. Proposal: single-currency v1, FX as a named non-goal. Agree?
4. **Cost basis / P&L.** Excluded from v1 above. Counter-argument: without any P&L, is it "portfolio accounting" or just position-keeping? Possible middle: average-cost only, no lot selection, P&L as a *derived read* (never stored) so it inherits P2's replay guarantee for free.
5. **gRPC accessory.** Worth ~2 days if it converts a ❌ honestly; skip if it delays the twins. Decide after P1–P3 are green.
6. **Second implementation for P5.** The reconciliation "independent statement": a stdlib-only Python twin of the fold (the intent-plane verifier pattern — byte-compared, import-pinned to run none of the Go code)? Strong rhyme, real cost. Alternative: fixture custodian files only.
7. **Sequencing vs. intent-workbench.** Both are approved-or-seeded builds competing for the same weeks. The ledger serves the distributed-systems application lane; the workbench serves a separate internal-tooling lane. Which lane is hotter decides the order — that's a pipeline question, not a design question, but it should be answered before either build starts.
